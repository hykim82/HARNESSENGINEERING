## 2. 대조 규칙(코드로 내린 선택)

PM 설계 §(c)는 여러 지점을 [추론]으로 열어 두었다. 이 라운드가 고른
구체값:

- **대조 키 1순위** = 보내는함/받는함 본문의 `전달 #<번호>` 토큰과
  전달 파일 머리줄 번호의 완전 일치.
- **대조 키 2순위**(번호가 없는 출처) = PM 설계 §(c) 원문 "시각 창
  ±15분(분 자리가 `x`면 ±10분) **그리고** 인용 앞 8글자 일치 또는
  같은 창 안 한용 항목 존재" 그대로 — 시각 창 **안에서만** 매칭으로
  친다(2R, HYK-255-relay-aux-2 P1-1). 창 안의 전달 항목이 하나라도
  있으면 그 disjunct("같은 창 안 한용 항목 존재")가 이미 참이라,
  창 안에서는 인용이 같든 다르든 매칭이다 — 구현도 그래서 시각 창
  존재만으로 판정한다(인용 앞 8글자 비교는 창 밖에서는 평가하지
  않는다). ⛔1R은 이 "그리고"를 "또는"으로 잘못 넓혀 창 밖 인용 일치도
  매칭으로 쳤다(근거-부록 C의 "시각 창까지 쓰면 대응 없음이 9건에서
  1건으로 줄어든다"는 "창을 더하면 줄어든다"는 근거였을 뿐, "창 밖
  인용 일치도 매칭"의 근거는 아니었다 — 검토 1R P1-1).
- **같은 분 다중 인용** = S1·S2를 합친 뒤 분(floor) 단위로 먼저 본
  것만 남긴다.
- **ㄱ-7 기록 누락**(오탐 방지 ⓑ) = 대응 없는 보내는함 항목이라도
  파일 이름이 `판정-<HHMM>`이고 받는함에 "같은 날짜 + 같은 HHMM"의
  `상신` 파일이 있으면 ㄴ 후보가 아니라 별도 칸으로 센다. 날짜·HHMM
  둘 다 파일 이름의 구조화된 `YYYY-MM-DD-HHMM` 토큰에서 뽑아 대조한다
  (2R P2-4 — 부분 문자열 포함(`includes`)만으로 대조하면 다른 날 같은
  HHMM, 또는 이름 어딘가에 같은 네 자리가 낀 파일까지 짝으로 잡힌다,
  검토 1R P2-4).
- **형식 이전 구간** = 전달 파일에서 실제로 관측된 가장 오래된 유효
  머리줄 시각보다 앞선 출처 항목은 "형식 이전 · 미계수"로 따로 센다
  (소급 0 — PM 설계 §(b) "소급은 하지 않는다"). 유효 머리줄이 아직
  하나도 없으면(형식 시작 시각 자체가 없음) 전달 파일의 정규식 밖
  줄·중복 번호도 "형식 이전 · 미계수"로 간다 — 아직 시작되지 않은
  형식을 어겼다고 소급해서 몰아세우지 않는다(2R P2-2, 아래 참조).
- **형식 오류** = 중복 번호(처음 것만 유효, 그 뒤는 전부 형식 오류) +
  `[책임자 경유 · ` 로 시작했지만 전체 정규식에 안 맞는 줄 — **단
  형식 시작 시각이 이미 있을 때만**(형식 머리줄이 0개면 전부 위
  "형식 이전" 칸으로 간다, 2R P2-2).

## 2-R. HYK-255-relay-aux-2(검토 1R 반려 수리)

검토 1R(`hyk255-relay-aux-1-review-1/.harness/review.md`)이 P1 1건 ·
P2 4건을 들었다. 책임자 판정(B-9, 1320 상신 답)은 전부 "PM 설계 문면
복귀"로 추천대로 확정했다 — 새 설계는 0이다.

- **P1-1**(대조 키 2순위 "또는"→"그리고") = 위 §2 "대조 키 2순위"
  항목 그대로. 1R 시험 "인용 앞 8글자만 일치해도(시각 창 밖이라도)
  대응으로 센다"를 뒤집었다(이제 "시각 창 밖이면 … ㄴ 후보로 센다").
- **P2-1**(개별 읽기 실패가 안 보임) = `renderRelayLedgerAuxLines`
  (ㄴ 절 보조 줄)와 `buildRelayLedgerNoticeText`(받는함 통지) 둘 다
  `relayReadFailures.length > 0`이면 "· 읽기 실패 N건"을 덧붙이고,
  "대응 없음(ㄴ 후보)" 수치에 "(전달 파일 읽기 실패로 불확실)" 괄호를
  붙인다 — 읍기 실패가 있으면 K를 확정값처럼 보이지 않게 한다.
- **P2-2**(형식 시작 전 옛 줄이 형식 오류 E로 소급 계수됨) = 위 §2
  "형식 이전 구간"·"형식 오류" 두 항목 그대로. ⛔1R 지시서(ⓒ⑶)가
  "정규식 밖 머리줄"을 시각 조건 없이 적어 작성자는 계약대로 했지만
  PM 설계 §(b) "소급 0"과 어긋났다(ORCH 자인, 1320 상신 §3) — 2R
  지시서가 "형식 시작 전 줄 = 형식 이전 칸"으로 명시했다.
- **P2-3**(짝 없는 `전달 #번호`가 2순위로 샘) = `matchOneSourceItem`에서
  `item.number`가 있으면 번호 일치 여부로 즉시 "matched"/"candidate"를
  정하고, 2순위(시각 창)로 넘기지 않는다 — "없는 번호를 가리킨다"
  자체가 ㄴ 후보 신호다.
- **P2-4**(ㄱ-7 날짜 무시) = 위 §2 "ㄱ-7 기록 누락" 항목 그대로.

## 3. 한계(⛔줄이지 마라)

- 새 출처(전달 파일·보내는함·받는함)는 전부 같은 계정이 쓸 수 있는
  파일이다 = 보조 관측. 1-C 판정 자격 "없음"은 무변이다.
- 머리줄을 쓰는 규율(책임자가 매 항목 1줄을 더 쓰는 것) 자체는 CI
  밖이다 — 이 라운드가 지키는 것은 "안 쓰면 형식 오류 E · ㄴ 후보 K가
  값으로 보인다"는 것뿐이다.
- S3(책임자 세션 jsonl)·채팅 밖 채널은 미탐이고 크기를 알 수 없다
  (PM 설계 §(c) "미탐 방향").
- 라이브 실물 결과는 이 라운드가 병합되고, 책임자가 예약 감시
  (`OrchStallWatch`)에 `--relay-glob`/`--inbox-dir` 인자를 추가하고,
  전달 파일에 머리줄 형식이 실제로 시작된 뒤의 첫 회차에서만 값으로
  나온다.
