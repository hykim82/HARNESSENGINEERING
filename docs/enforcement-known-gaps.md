# Enforcement known-gaps table (NC-1 + NC-2 + NC-3)

**정직 한계**: 이 표에 없는 장치는 검사되지 않았다는 뜻이며, 표의 완전성은
`scripts/check/enforcement-inventory.json`(손으로 유지되는 매니페스트)에
의존한다. 이 표는 현재 NC-1 범위(`review-gate` · `quality-check` ·
`pre-commit-gitleaks` + 설치·발동 확인, #1~#10) **와** NC-2 범위(릴레이·레인
4장치 — `relay-handshake` · `reject-streak` · `role-guard` ·
`go-task-id-gate`, #11~#24) **와** NC-3 범위(경계·환경 2장치 —
`ci-enforce` · `orca-automations-present`, #25~#29)를 다룬다. NC-2 행은
#11부터, NC-3 행은 #25부터 이어 붙인다.

**★NC-3로 v1 의존 강제 장치 9개 전수가 negative-control로 덮였다**(NC-1
3+설치·발동 + NC-2 4 + NC-3 2 = 9/9). 다만 이 "전수"에는 **완전성 한계가
있다**: (1) 이 9개의 목록 자체가 `scripts/check/enforcement-inventory.json`
이라는 **손으로 유지되는 매니페스트**에서 나온 것이라, 매니페스트에
등록되지 않은 강제 장치가 있다면 애초에 이 트랙의 시야 밖이다. (2)
`ci-enforce`·`orca-automations-present` 둘 다 **저장소 밖 표면**(GitHub
저장소 설정·branch protection·실제 `%APPDATA%\orca\orchestration.db`)에
걸쳐 있어, 이 트랙이 실제로 시험할 수 있는 것은 **저장소 안의 텍스트
계약**(추적된 워크플로 파일 · 순수 함수 export)뿐이고 저장소 밖 실체(실제
GitHub 저장소 설정 자체·실제 Orca 설치 상태)는 읽기 전용 관측 1회
(§4-3) 또는 아예 손대지 않음(§2 비타협 #2)으로 남는다. (3) `orca-automations-present`는
**Orca 벤더의 로컬 파일 레이아웃**(SQLite 스키마·인코딩)에 의존하며, Orca
업데이트로 그 레이아웃이 바뀌면 이 장치의 판정 정확도도 드리프트할 수
있다 — 이 트랙은 오늘 시점의 동작만 고정한다.

이 표는 저장소 안(신규 파일)이므로 **PR 없이는 지워지지 않는다**. 근거·재현
방법 열은 재현 가능한 테스트를 가리키며, 그 테스트가 지워지거나 assert가
바뀌면 이 행의 근거도 무효가 된다 — 리뷰어는 재현 테스트가 실제로 이 행이
말하는 것을 단언하는지 확인해야 한다.

## 검증 위치 표준(L1/L2/L3) — 2026-07-30 핫픽스에서 확정

**"측정 위치가 결과를 바꾼다"를 이 트랙에서 세 번 겪었다**(워크트리 skip
2건/메인 저장소 skip 0건 · CRLF vs LF 위치 의존 DRIFT(gap #9) · 이번
회귀 — 메인 저장소에서만 실패). 그래서 `nc-githook-install.test.mjs`류
"설치 상태" 관련 시험을 검증할 때는 아래 **세 위치를 항상 함께** 재고,
그 결과를 이 표에 남긴다. 하나만 재고 "검증했다"고 말하면 이 표가
막으려는 바로 그 형태의 잘못된 안심이다.

## 검증 위치 표준에 추가된 두 축 (NC-2, 2026-07-31)

### cwd 축

같은 위치·같은 명령이라도 **어느 디렉터리에서 실행하느냐**(저장소 루트
vs `scripts/` 하위)에 따라 결과가 갈릴 수 있다(2026-07-30 NC-1 핫픽스
2R에서 REVIEW가 지적했으나 이 표에는 미등재였던 미결 항목). NC-2에서
L1을 두 cwd에서 직접 재실측했다(§6 실측 로그 참조):

| cwd                          | 명령                                                                           | 결과                              |
| ---------------------------- | ------------------------------------------------------------------------------ | --------------------------------- |
| 저장소 루트                  | `node --test scripts/check/*.test.mjs ...`(전체 glob)                          | tests/pass/fail 수 — §6 L1 로그 1 |
| `scripts/`(저장소 루트 하위) | `node --test check/*.test.mjs check/../relay/*.test.mjs ...`(상대 glob 재작성) | tests/pass/fail 수 — §6 L1 로그 2 |

NC-2가 신설한 4개 시험(`nc-relay-handshake` · `nc-reject-streak` ·
`nc-role-guard` · `nc-go-task-id-gate`)은 전부 대상 모듈을 **정적 상대
`import`**(예: `import { checkRelayHandshake } from
"./relay-handshake.mjs"`)로 불러온다 — ECMAScript 모듈의 상대 `import`
경로는 **그 import를 쓴 파일 자신의 위치 기준**으로 해석되며 실행
cwd와 무관하므로, 이 부분은 **cwd 축과 애초에 접점이 없다**(2R
REVIEW 정정: "repo root를 구해 절대경로로 import한다"는 1R 서술은
부정확했다). `execFileSync("git", ["rev-parse", "--show-toplevel"])`는
각 시험 파일이 **원상복구(전후 불변) 확인**(`git status --porcelain`·
`git diff HEAD --stat`을 시작 전/후 캡처해 비교)에만 쓰며, 대상 모듈
import와는 무관하다. **결론(새 시험은 cwd 비의존)은 §6 두 cwd 실측
숫자가 동일함으로 여전히 유지**되며, 이번 사이클에서 새로 발견된 cwd
의존 결함도 없다 — 다만 그 비의존성의 **근거**가 "절대경로 import"가
아니라 "정적 상대 import는 애초에 cwd를 보지 않는다"는 점이라는 게
2R 정정의 요지다.

### 플랫폼 축 (신규 · 2026-07-31 실사고 반영)

**L1·L2·L3가 전부 이 머신(Windows)이라, 호스트 OS에 의존하는 결함은 세
위치 어디서도 못 잡는다.** 2026-07-31 PR #76의 첫 커밋이 정확히 이
형태였다(`node:path.basename`이 리눅스에서 Windows 경로를 미탐지) —
**리눅스 CI가 유일한 반증 자리**였다.

**NC-2 4장치 자체 점검(플랫폼 의존 가능성)**:

- `relay-handshake.mjs` · `reject-streak.mjs` · `go-task-id-gate.mjs`:
  경로 조립에 `node:path`의 `join`만 쓰고, 파싱은 전부 정규식(문자열
  단위)이다 — `basename` 등 호스트 OS 규칙에 의존하는 함수를 쓰지
  않는다. NC-2 테스트 파일 자신도 같은 원칙을 지켰다(백슬래시/슬래시를
  정규식·직접 문자열 치환으로만 다룸, `path.basename` 미사용).
  **플랫폼 의존 가능성 낮음.**
- `role-guard.mjs`가 위임하는 `path-normalize.mjs`는 `node:path`의
  `posix.normalize`만 쓰고(플랫폼 고정, `path.win32`/OS 자동분기 아님)
  나머지는 직접 정규식으로 드라이브 문자·백슬래시를 다룬다 —
  **`posix.normalize` 사용 자체가 이미 "호스트 OS와 무관하게 항상
  POSIX 규칙"을 선택한 설계이므로 플랫폼 의존 가능성 낮음.** 단,
  `nc-role-guard.test.mjs`의 경로 표기 변형 시험(`..`·대소문자·
  슬래시/백슬래시)은 전부 이 머신(Windows)에서만 실측됐다는 점은
  정직하게 남긴다 — **증명력은 로컬 3위치 한정이며, 최종 반증 자리는
  PR의 리눅스 CI**다.
- 결론: 이번 NC-2 시험 4개 중 **호스트 OS 규칙에 실제로 의존하는
  코드 경로는 발견되지 않았다**(근거: 위 점검, 3-2/3-3/3-4 소스 직접
  읽음). 그러나 "의존 코드가 없어 보인다"는 이 4장치·이 시험 파일에
  한정된 로컬 판단이며, PR #76 사고 자체가 "로컬 3위치 전부 초록이어도
  실제로는 플랫폼 의존이었다"는 반례이므로 **이 결론에도 로컬 3위치의
  증명력 한계가 그대로 적용된다**.

⚠️ **4R 안심 방지 고지(중요·잘못된 안심 방지)**: `.github/workflows/enforce.yml`
9단계를 전수 확인한 결과 **CI는 어떤 단계에서도 `.git/hooks/*`를 설치하지
않으며**(`package.json`에 `prepare`/`postinstall` 스크립트도 없음), CI가 도는
`scripts/check/*.test.mjs` glob에는 이 저장소의 훅 **설치 상태**를 재는 시험도
포함된다. 그래서 4R부터 `nc-githook-install.test.mjs`의 "설치된 훅 현재 상태"를
재는 시험은 전부 **환경 조건부**(설치본이 실제로 있을 때만 돌고, 없으면
`skip`)로 만들었다. **결론: 이 저장소의 CI가 초록이라는 사실은 어떤 개발
머신에도 훅이 실제로 설치돼 있다는 것을 전혀 보장하지 않는다** — CI가
검사하는 것은 (a) 추적본(`hooks/*`) 기준 계약(항상 성립)과 (b) 완전 합성
픽스처로 고정한 결함 재현(항상 성립)뿐이다. 설치 상태 자체는 사람이 각
머신에서 직접 확인해야 한다(#7·#8 행 참조).

⚠️ **4R 추가 발견(당시 계약 밖·수리 안 함)** — **5R에서 해소됨(아래 참조)**:
같은 CI 근사 조건(`mkdtemp` 단일 체크아웃 클론)에서 `scripts/check/
nc-*.test.mjs` 전체를 돌려본 결과, `nc-gitleaks.test.mjs`의 `"NC-1
gitleaks/gap: 'gitleaks not installed' fail-open branch ..."` 시험도
**동일한 원인 계열**(설치된 `.git/hooks/pre-commit`을 무조건 읽음)로 이
조건에서 실패함을 발견했다. 당시(4R) 그 파일은 §11이 명시한
`nc-githook-install.test.mjs`의 6건에 포함되지 않아 수리하지 않고
정직 보고만 했다.

⚠️ **5R 해소**: 위 4R 발견이 이번 라운드(§12)의 단일 계약이 되어 고쳤다.
이 시험의 목적은 "훅 스크립트 텍스트에 fail-open 분기가 문서화됐는가"
확인이며, 그렇다면 설치본이 아니라 **추적본 `hooks/pre-commit`**(모든
체크아웃·CI에 항상 존재, CI가 이미 `sh -n`으로 문법 검사하는 바로 그
파일)을 읽는 편이 목적에 더 맞고 CI에서도 성립한다 — 그렇게 바꿨다.
설치본에 대한 확인은 **환경 조건부 부가 측정**(`"NC-1 gitleaks/
measurement (environment-conditional): the INSTALLED pre-commit copy
(when present) also documents the fail-open branch"`)으로 분리해
설치본이 있을 때만 돌고 없으면 정상 skip되게 했다. 단일 체크아웃
클론에서 `scripts/check/nc-*.test.mjs` 전체 재실측: tests 38·pass
34·**fail 0**·skip 4.
