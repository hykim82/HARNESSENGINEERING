# approval-authority-adapter.mjs -- mutation ledger (HYK-183 v1c2b)

방법: `scripts/supervisor/approval-authority-adapter.mjs`를 Edit로 직접 변형 →
`node --test --test-name-pattern="<name>" scripts/supervisor/approval-authority-adapter.test.mjs`로
관련 테스트만 실행해 RED를 실측 → `/tmp/aaa-backup.mjs`(변형 전 원본 백업)로 복원 → 다음 변형.
전 과정 후 `diff /tmp/aaa-backup.mjs scripts/supervisor/approval-authority-adapter.mjs`로
원본과 바이트 단위 동일함을 확인했다(코드는 이 원장 작성 과정에서 1바이트도 바뀌지 않았다).

1R 15건 + 재작업 2R 3건 + 재작업 3R 2건 = 총 20건. REVIEW 1R가 요구한 필수
항목(§3-2의 4·6·명단 origin/master 고정·id 일치·`user.type` 무의존), REVIEW
1R가 반려한 P1 5건 중 신규 방어선을 요구한 3건(P1-1 throw 흡수·P1-2 리뷰
payload 형태 검사·P1-3 명단 schema_version), 한용 게이트 2가 지시한
`submitted_at` 정렬 판별력 2건(coder-task.md §11) 전부를 포함한다.

## 관찰

- 20건 모두 실제로 `node --test`를 돌려 RED를 관측했다(추정·서술 아님).
- #1·#2·#10 세 건은 "차단이 승인으로 바뀌는" 유형이 아니라 "사유 코드/분류가 틀리는" 유형이다 --
  둘 다 §3-1의 "판정을 지어내지 않는다"는 요구를 어기는 것으로 간주해 포함했다
  (사유가 틀리면 사람이 왜 막혔는지 오판한다).
- #13(origin/master 고정)은 이 코드베이스의 가짜 git 포트 설계상 "계약 밖 호출은 throw"로
  단언하는 방식이라, 변형 결과가 곧바로 위조 성공(`APPROVED`)으로 나타나지 않고 계약 위반
  자체가 감지된다. 그럼에도 원래 기대값(`NOT_APPROVED`)과 달라졌으므로 RED로 카운트했다 --
  실제 운영에서 이 자리를 무력화하면(다른 git 포트라면) 위조 명단이 곧바로 읽힐 것이다.
